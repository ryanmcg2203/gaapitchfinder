How I Gave a Static Side Project a CDN for €0

18 October 2026 · 4 min read

GAA Pitch Finder is a static website. There are no application servers, no database, and no complicated backend running behind it. GitHub Pages hosts the site, and GitHub is the source of truth for the code and data.

Recently, I added Cloudflare in front of it. That sounds more elaborate than it really is, but it has given the site a useful little edge-caching layer without me having to run any infrastructure myself.

The setup

The main map loads a generated data.json file containing the pitch dataset. Cloudflare now sits between the visitor and GitHub Pages:

Browserrequests data.json
↓
Cloudflareedge cache
Cache hit: return the cached file
Cache miss: fetch it from the origin
↓
GitHub Pagesorigin and source of truth

I created a cache rule specifically for /data.json, with an edge TTL of two hours.

Cache misses and cache hits

When a request reaches Cloudflare, it checks whether it already has a fresh copy of the file.

  • On a cache miss, Cloudflare fetches data.json from GitHub Pages and stores a copy.
  • On a cache hit, Cloudflare returns its cached copy without needing to go back to GitHub Pages.

The satisfying part was seeing the headers confirm that it was working:

CF-Cache-Status: HIT
Age: 62

CF-Cache-Status: HIT means the response came from Cloudflare's cache. The Age header shows how long that cached object had been sitting there when it was requested.

Cloudflare's cache is distributed across its edge locations, so there is not one single magical global copy. A particular location may have a miss first, followed by hits for later requests there. But the principle is the same: serve repeated reads from a nearby cache instead of repeatedly fetching the same file from the origin.

There is another cache too

The browser can cache the file locally as well. In this case, the response includes:

Cache-Control: max-age=14400

That is 14,400 seconds, or four hours. This is separate from the two-hour Cloudflare edge TTL:

  • The edge TTL controls how long Cloudflare considers its copy fresh.
  • The browser max-age controls how long a visitor's own browser can reuse its local copy.

It is easy to talk about “the cache” as though there is only one, but there are really several layers between the code and the user.

Why this works well for GAA Pitch Finder

The pitch dataset is a good fit for caching because it is read-heavy and the answer is the same for everyone until the data changes. There is no reason to generate a different response for each visitor.

In simple terms, GitHub Pages remains the authoritative source, Cloudflare becomes the distribution layer, and the browser can keep a local copy for a while.

This is the same broad pattern used in much larger systems: an authoritative source behind a cache, with many users reading the cached result. The difference is that this version is running in front of a small static side project, using tools I already had available.

A small project, a useful lesson

I like this kind of improvement because it is practical rather than flashy. I did not need to introduce a server, a database, Redis, or a separate CDN setup. I just identified the read-heavy part of the site and put an appropriate caching rule in front of it.

GAA Pitch Finder started as a map. It now has an open dataset, automated builds, generated pages, an R package built by someone else, and a small edge-caching architecture sitting in front of it. Not bad for a side project about GAA pitches.
