# Derived Data

This directory is for dataset files that are generated from the canonical
`gaapitchfinder_data.csv` source file.

Typical flow:

- `gaapitchfinder_data.csv` is the base dataset.
- enrichment or analysis scripts read that file.
- durable generated datasets and coverage reports are written here.
- site assets and charts are generated separately under `site/` and `output/`.

Current files:

- `osm_coverage_report.csv`: OSM pitch coverage report
- `pitch_geometry.csv`: generated by `scripts/enrich_pitch_geometry.py` when run locally
- `club_wikipedia_links*.csv`: review-first Wikipedia/Wikidata link suggestions generated by `scripts/enrich_club_wikipedia.py`

## OSM Coverage Refreshes

`scripts/analyze_osm_coverage.py Monaghan Down` refreshes every current canonical
record in the named county groups. It replaces those complete county partitions
in the existing report and retains other counties unchanged. This avoids matching
by club name alone: a club may have multiple pitches, while a refreshed partition
must also reflect removed or moved records. Stable record IDs and richer snapshot
lineage remain follow-up work in issues #140 and #134.

Partial runs require a nonempty, readable report. Unknown county arguments (even
when mixed with valid ones) and unsupported report formats fail before API calls
or writes. A run without county arguments builds a new report from all current
canonical county groups and replaces the previous report. County labels retain
their existing dataset meaning, including overseas groups; this change does not
redefine the analysis population addressed in #134.

The CSV retains `Club`, `County`, `Province`, `Latitude`, `Longitude`, and `Status`,
and adds `CheckedAt`: the UTC time of that record's latest check attempt. Legacy
six-column reports are supported, with unknown historical check dates left blank.
Unrefreshed records keep their previous dates, so a new file commit must not be
interpreted as a new check of every location.

API failures replace the selected record's previous status with `api_error` and
the latest attempt time; they are not successful negative matches. `no_coords`
likewise means unavailable. The console coverage percentage excludes both statuses
and displays `N/A` when no records were evaluated, consistent with the dashboard.
Rerun the affected counties to retry. Unexpected worker exceptions abort publication
and retain the previous report.

The complete report is serialized and flushed to a temporary file in the output
directory, then published with one atomic replacement. Interrupted writes leave
the prior report intact. Run only one refresh process against this output at a time.

Regression tests use temporary datasets and mocked API responses:

```bash
python3 -m unittest discover -s tests -p test_osm_coverage.py
```

## Geometry Enrichment Resume

`scripts/enrich_pitch_geometry.py` stores both CSV results and processed row
indices in `data/derived/.pitch_geometry_checkpoint.json`. This versioned snapshot
is the authoritative resume state; `pitch_geometry.csv` is its exported view.
Do not edit the generated CSV to change resume state: a successful resume restores
the export from the snapshot, including when the export is missing or stale.

The snapshot is replaced atomically only after the complete file is flushed.
Results and completion markers therefore commit together. An interruption before
that replacement retains the previous snapshot; an interruption during the CSV
export is repaired on the next run. Progress is saved every ten iterations and at
normal completion, so an interrupted run may repeat work since its last save.
API failures remain unprocessed and are retried on a later run.

Until persistent record IDs are available, positional results are valid only for
the exact source CSV bytes. Reordering, adding, deleting, renaming, or moving a
record causes resume to fail before requests or writes. Changes to the enrichment
script, query radius, or endpoint also invalidate resume. This intentionally
favours safety over reusing results across dataset revisions.

Legacy index-only checkpoints and standalone CSV exports cannot prove their
association with the input and are rejected. To start again, archive **both**
`pitch_geometry.csv` and `.pitch_geometry_checkpoint.json` outside their normal
paths, then rerun the script. Keep the archived pair for reference; there is no
automatic destructive reset or automatic migration of unverified old results.
Run only one geometry enrichment process against these paths at a time.

The standard-library persistence regression tests run with the normal suite:

```bash
python3 -m unittest discover -s tests -p test_geometry_checkpoint.py
```

The same command also runs the mocked end-to-end enrichment test when the optional
analysis dependencies in `requirements.txt` are installed (otherwise that test is
skipped). No tests make Overpass requests.

## Wikipedia Link Enrichment

`scripts/enrich_club_wikipedia.py` searches Wikidata for possible Wikipedia
links for each grouped club record. It writes suggestions only; links should be
reviewed before being used on the public site.

Useful commands:

```bash
python3 scripts/enrich_club_wikipedia.py --limit 25
python3 scripts/enrich_club_wikipedia.py --county Leitrim --county Monaghan
python3 scripts/enrich_club_wikipedia.py --club "Portobello GAA"
python3 scripts/enrich_club_wikipedia.py --county Leitrim --workers 2
python3 scripts/enrich_club_wikipedia.py --county Leitrim --county Monaghan --output data/derived/club_wikipedia_links_leitrim_monaghan.csv
python3 scripts/enrich_club_wikipedia.py --min-confidence 80
```

The output includes a `match_status`:

- `suggested`: high-confidence candidate with an English Wikipedia page
- `needs_review`: possible match, but not strong enough to trust automatically
- `no_match`: no useful Wikidata candidate found
- `api_error`: Wikidata request failed and should be retried later
